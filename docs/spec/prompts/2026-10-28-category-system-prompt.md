# 任务：为现有 Flutter 记账 App 实现完整的分类管理系统

你是一名资深 Flutter 工程师和移动端产品设计师。请基于当前已有的 Flutter + Dart 项目，实现一套完整、易用、可扩展的记账分类管理功能。

## 一、开发原则

1. 首先检查现有项目的目录结构、技术栈、状态管理方式、数据库实现、账单数据模型和 UI 风格。
2. 优先复用现有架构和组件，不要擅自更换状态管理方案、数据库或 UI 框架。
3. 不要重写整个 App，不要破坏现有的记账、账单列表、账单详情和统计功能。
4. 如果项目已经存在分类相关的数据表或代码，应在现有基础上升级，避免重复创建或造成数据丢失。
5. 所有功能必须实际实现，不要只生成静态 UI、伪代码或演示数据。
6. 遵循 Flutter 最佳实践，保持代码结构清晰、职责分离、易于测试和维护。
7. 适配 Android 手机屏幕，兼容 Android 14。
8. 开始修改前，先简要说明现有项目结构和实施方案，然后继续完成实现，不要只停留在方案说明阶段。

## 二、分类功能需求

### 1. 收入和支出分类分离

分类管理页面顶部设置两个切换选项：

- 支出分类
- 收入分类

两种类型独立管理，不能将收入分类错误地用于支出账单，反之亦然。

为首次使用的用户提供合理的默认分类。

支出默认一级分类建议：

- 餐饮
- 交通
- 购物
- 居住
- 娱乐
- 医疗
- 教育
- 人情社交
- 旅行
- 通讯
- 其他支出

收入默认一级分类建议：

- 工资
- 奖金
- 兼职
- 投资收益
- 退款
- 红包礼金
- 其他收入

可以为常见分类配置适当的图标、颜色和排序。

默认分类只应在首次初始化时创建，不能在每次启动 App 时重复插入。

### 2. 支持一级分类和二级分类

分类支持树形结构：

- 一级分类的 parentId 为空。
- 二级分类通过 parentId 关联父分类。
- 支持创建一级分类。
- 支持在一级分类下创建二级分类。
- 支持编辑分类名称、图标和颜色。
- 支持调整分类顺序。
- 分类层级限制为两级，避免无限嵌套。

二级分类应当是可选功能。用户可以直接选择一级分类记账，不需要强制选择二级分类。

### 3. 分类管理页面

设计简洁、现代、清晰的移动端界面，融入现有 App 的设计风格。

页面布局建议：

- 顶部标题：分类管理。
- 顶部 Tab：支出、收入。
- 分类列表以分组方式展示。
- 一级分类显示图标、名称及操作入口。
- 二级分类缩进展示。
- 提供新增分类按钮。
- 支持编辑、排序、归档和删除。
- 空状态提供明确的操作引导。
- 删除或归档前，根据实际影响显示确认提示。

不要将页面做成复杂的后台管理系统。优先考虑单手操作、清晰的信息层级和较少的操作步骤。

### 4. 新增与编辑分类

新增或编辑分类时，支持以下字段：

- 分类名称，必填。
- 分类类型：收入或支出。
- 父分类，可选。
- 图标。
- 颜色。
- 排序位置。

要求：

- 分类名称去除首尾空格。
- 禁止空名称。
- 同一分类类型、同一父分类下，不允许出现重复名称。
- 校验失败时显示明确的提示。
- 编辑时正确回显原有信息。
- 修改后立即更新相关 UI。
- 不允许将分类设置为自己的子分类。
- 不允许超过两级分类。

### 5. 分类图标和颜色

提供适合记账场景的图标选择器和颜色选择器。

要求：

- 优先复用项目已有的图标和颜色方案。
- 如果没有现成方案，可以使用 Material Icons 或 Flutter 自带图标。
- 图标和颜色需要持久化保存。
- 避免直接将 Flutter IconData 的运行时 hashCode 作为持久化标识。
- 建议使用稳定的图标 key，并在代码中维护 key 到 IconData 的映射。
- 自定义颜色使用稳定的整数颜色值保存，并正确处理透明度。

### 6. 分类排序

支持用户调整分类显示顺序。

要求：

- 一级分类支持拖拽排序。
- 二级分类支持在同一父分类内拖拽排序。
- 不允许通过拖拽意外改变分类层级。
- 排序结果持久化到数据库。
- 重新进入页面后顺序保持不变。
- 如果现有项目不适合实现拖拽，可以提供上移、下移操作作为可靠替代方案。

### 7. 删除、归档与历史账单保护

必须特别注意历史数据安全。

删除或归档分类时：

- 如果分类没有关联任何历史账单，可以允许真正删除。
- 如果分类已经被历史账单引用，默认采用归档，而不是物理删除。
- 归档分类不再出现在新建账单的常规分类选择列表中。
- 历史账单仍然可以正确显示原分类名称、图标等信息。
- 历史账单编辑时，应能正确处理已经归档的分类。
- 如果一级分类下存在二级分类，需要明确处理子分类，不能留下无效的 parentId。
- 删除操作必须考虑数据库事务和外键约束。

如果用户希望删除一个仍被使用的分类，应提供明确选择，例如：

1. 归档分类，保留历史账单。
2. 将关联账单迁移到另一个兼容类型的分类，然后删除原分类。

迁移账单时，必须保证账单金额、日期、备注、账户等其他数据不变。

禁止静默删除历史账单或留下无法识别的分类。

## 三、数据模型和数据库

首先检查项目现有的数据库方案。如果已有 SQLite、Drift、Isar、Hive 或其他持久化方案，优先沿用，不要为了本功能引入不必要的新数据库。

分类实体至少需要表达以下信息：

- id：稳定且唯一的分类标识。
- name：分类名称。
- type：expense 或 income。
- parentId：可空的父分类 ID。
- iconKey：稳定的图标标识。
- colorValue：颜色值。
- sortOrder：排序位置。
- isSystem：是否为系统预置分类。
- isArchived：是否归档。
- createdAt：创建时间。
- updatedAt：更新时间。

具体字段类型、主键生成方式和命名规范应适配现有项目。

账单与分类之间应通过稳定的分类 ID 关联，不要依赖分类名称进行关联。

需要注意：

- 如果现有账单表已经有分类字段，应尽可能兼容现有结构。
- 数据库升级必须提供必要的 migration。
- 不能因为新增字段或修改模型而丢失用户现有数据。
- 如果数据库支持外键，应根据现有设计合理配置。
- 对分类查询、账单关联和统计查询进行必要的索引优化。
- 处理分类不存在、归档、迁移和旧数据兼容的情况。

## 四、业务逻辑和代码架构

根据项目现有架构，实现相应的：

- Category Model / Entity。
- Category Repository。
- 分类增删改查逻辑。
- 分类初始化逻辑。
- 分类排序逻辑。
- 分类归档和迁移逻辑。
- 分类管理页面。
- 新增与编辑分类页面或弹窗。
- 图标与颜色选择组件。
- 与现有记账页面的分类选择组件集成。

状态管理必须沿用项目已有的方案，例如 Provider、Riverpod、Bloc、GetX 或其他已有实现，不要无理由引入第二套状态管理方案。

要求：

- UI 不直接承担数据库操作。
- 业务逻辑和持久化逻辑分离。
- 异步操作应正确处理加载状态、成功状态和异常状态。
- 新增、编辑、归档、排序后，相关页面的数据应及时刷新。
- 避免不必要的重复查询和重复初始化。
- 错误信息应清晰，不要吞掉异常。

## 五、与现有记账流程集成

这是本任务的重要部分，不能只完成分类管理页面。

请检查现有的新增账单和编辑账单流程，并完成集成：

1. 新建支出账单时，只显示有效的支出分类。
2. 新建收入账单时，只显示有效的收入分类。
3. 选择一级分类时，可以直接完成选择，也可以继续选择二级分类。
4. 选择二级分类时，正确关联其父分类。
5. 编辑历史账单时，正确显示原分类。
6. 分类被重命名后，历史账单应显示更新后的名称。
7. 归档分类不能被普通新账单选择，但历史账单不能因此丢失分类信息。
8. 删除或迁移分类后，账单列表、详情页和统计页面必须保持一致。
9. 如果统计功能使用分类 ID 或分类名称进行聚合，应检查并修复相关逻辑。
10. 不要擅自改变现有金额计算、账户余额和收支统计规则。

如果项目已有最近使用或常用分类功能，请保持兼容；如果没有，可以将它作为可选扩展，不要因此阻塞核心功能实现。

- 所有操作提供清晰的反馈。

- 避免无意义的确认弹窗。
- 分类列表支持合理的滚动和触控区域。
- 图标、名称、颜色应有足够的视觉区分度。
- 适配深色模式（如果现有 App 已支持）。
- 避免因屏幕尺寸较小出现溢出。
- 遵循现有主题、字体、间距和导航风格。
- 不要使用大量硬编码的 UI 样式破坏项目的一致性。

10. 一级分类及子分类删除、归档时不会产生孤立数据。
