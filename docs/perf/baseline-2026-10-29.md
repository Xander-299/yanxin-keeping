## 3. 测量方法与口径

### 3.1 启动（`Measure-Startup.ps1`）
- **冷启动**：`am force-stop` → 等 1.5s → `am start -W -n <pkg>/<activity>`。
- **热启动**：`KEYCODE_HOME`（进程保住、Activity 退后台）→ `am start -W`，输出里 `LaunchState=HOT` 作为证据。
- 记录三个量：`TotalTime`（am 报的启动总耗时）、`WaitTime`（调用方等待）、
  `Displayed`（logcat `ActivityTaskManager: Displayed … +0s636ms`，**首帧上屏**）。
- 冷启动下 `Displayed ≈ TotalTime`（差值 <5ms）；热启动系统**不打** Displayed 行，故为空。

**局限**：`TotalTime/Displayed` 只到"首帧上屏"，**不等于可交互**（Flutter 首帧后还有
`categoriesProvider` 查询、首屏列表构建）。真要测"能点下去"，需要 DevTools timeline 或打点。

### 3.2 页面流畅度（`Measure-Frames.ps1`）
- 设计：`dumpsys gfxinfo <pkg> reset` → 脚本化手势（首页上下滚 / 日历左右翻月）→ `dumpsys gfxinfo` 读掉帧率与百分位。
- **实际结果：0 帧**（三次都 0）。已排除"没开统计"：`Janky frames (legacy): 0`、百分位全是 4950ms 的占位值。
  改用 `dumpsys SurfaceFlinger --latency "<SurfaceView 层>"` 仍全 0（首行 16666667ns = 60Hz 说明层找对了）。
- **结论**：该机型 + Android 14 + Flutter（SurfaceView 呈现路径）下，这两条 adb 路径都统计不到帧。
  **记为「未测量」，不当作 0 卡顿。**

### 3.3 资源（`Measure-MemoryCpu.ps1`）
- 内存：`dumpsys meminfo <pkg>` 的 `TOTAL PSS`，每 8–9s 一次，采样之间滚动页面。
- CPU：`top -b -n 2 -d 1 -p <pid> -o PID,%CPU` 取第二帧（`dumpsys cpuinfo` 空闲恒 0，太粗）。
- **局限**：采样点在手势**之后**（App 已回空闲），所以 CPU 接近 0；PSS 不含 GL/图形内存单独项，
  45s 窗口也**不足以**判定内存泄漏（只能说明"短时稳定"）。

### 3.4 包体积（`Measure-ApkSize.ps1`）
- 临时把 `android/gradle.properties` 的内存参数降到 3G 并追加 `qaAppId`，**构建后按字节还原**（已验证）。
- 记录 APK 文件字节数；另用 `pm path` + `du -sk` 记录设备上已装 APK 本体大小。
- **APK 文件大小 ≠ 下载大小 ≠ 安装占用**：安装后还要解压 native libs 与 odex，通常更大；
  本报告只报"文件大小"和"设备上 APK 本体"，**完整安装占用未测**。

### 4.2 内存 / CPU（首页 + 滚动，profile）

| 采样 | 时间 | PSS | CPU |
|---|---|---|---|
| 1 | 3s | 214.1 MB | 0 % |
| 2 | 13s | 214.7 MB | 0 % |
| 3 | 24s | 214.2 MB | 0 % |
| 4 | 35s | 214.3 MB | 1 % |

- 峰值 215.2 MB 那组数据是**对着 debug 进程**采的（见 §0 的订正说明），作废。

#### 4.2.1 meminfo 明细（profile，冷启后 6s）

| 项 | PSS |
|---|---|
| Java Heap | 8.8 MB |
| Native Heap | 7.8 MB |
| Code | 13.9 MB |
| Stack | 0.5 MB |
| Graphics | 0 MB |
| Private Other | 1.6 MB |
| System | 7.0 MB |
| **TOTAL PSS** | **≈ 39.6 MB**（同一进程另一次采样 43.3–44.3 MB） |

**解读**：`Code 13.9 MB` 是 Flutter engine + 各 `.so` 的只读映射；`Java/Native Heap` 合计 ~17 MB 是业务与 Dart VM；
没有哪一块"异常大"。**结论：43 MB 对一个 Flutter + 本地数据库的记账 App 属正常区间，不需要为内存做优化。**

#### 4.2.2 ML Kit 是否在启动期加载 —— **否，已经是懒加载**

- Dart 侧：`ocrEngineProvider` 是 Riverpod 的普通 `Provider`（惰性），只在首次 `recognize` 时实例化；
- Kotlin 侧：`OcrChannel.ensureRecognizer()` 才 `TextRecognition.getClient(...)`，`attach()` 里没有预热；
- **运行时证据**：冷启 6s 后 `run-as cat /proc/<pid>/maps | grep -i 'mlkit|ocr'` → **零命中**，
  即 `libmlkit_google_ocr_pipeline.so` 与中文模型都没进内存。
- 所以"延迟到截图记账首次进入再加载"**已经是现状**，本轮**没有改代码**（不改就不会引入回归）；
  将来若有人给 OCR 加预热，用上面这条 `maps` 命令即可证伪。

## 7. 后续：让帧率也可自动测（需要你拍板）

Android 侧帧数据在 Flutter 上要靠引擎自己报。两条路：

1. **不加依赖（推荐先试）**：`flutter run --profile -d MRN7ONWCUSHYG65D` 后打开 DevTools → Performance，
   录制"首页滚动 / 日历翻月"，读 `Frame Chart` 的 build/raster 分布。人肉但零改动。
2. **加 `integration_test`（可自动化，但会动 pubspec）**：`dev_dependencies: integration_test: sdk: flutter`
   + `test_driver/perf_driver.dart` + `integration_test/perf_test.dart`，跑 `flutter drive --profile`，
   输出 `TimelineSummary`（average/worst frame build & raster time、missed frame count）。
   ⚠️ 风险：本仓库依赖是**锁死**的，`flutter pub get` 可能改 `pubspec.lock`；需要你确认后我再动。
