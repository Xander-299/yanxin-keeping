# Android 端本地 LLM 基准（阶段二任务 1）

> 目的：把 `docs/spec/SPEC-local-ai.md` §4.2 要求的那张「设备 × 模型」表做出来，
> **没有这张表就不许写「支持哪些机型 / 多快」的文案**（Prompt 阶段四）。
>
> 本文只放**实测数字与本轮结论**；测量口径的代码在 `tool/llm_bench/`（可复现）。

## 0. 一句话结论

**首选 Qwen2.5-1.5B-Instruct Q4_K_M**：在 Redmi K50 上 10 轮稳定 **7.4 tok/s** 生成、
**36 tok/s** 预填、常驻 **1.18 GB**、10 轮后 RSS 不涨；**连跑 20 分钟（68 轮）不掉速**（7.4 → 7.0，
大核从 2.85 GHz 降到 2.15 GHz 但吞吐不变，瓶颈是内存带宽）。
但**首 token 需要 3.5–5.1 s**（177 token 上下文）—— 这决定了产品口径：
**本机模型只能做「措辞层」，不能让用户等它算数**（数字一律由业务代码算好塞进上下文）。

## 1. 测试条件（写死，换机器要重测）

| 项 | 值 |
|---|---|
| 设备 | Redmi K50 `22041211AC`（`rubens`），1080×2400 |
| SoC | MT6895（Dimensity 8100）：**4×Cortex-A78 @2.85 GHz（cpu4–7）+ 4×Cortex-A55 @2.0 GHz（cpu0–3）** |
| 内存 | MemTotal 7 666 260 kB（≈7.5 GB）；测试时 MemAvailable ≈1.35 GB（用户日常使用中） |
| 系统 | Android 14 / HyperOS **V816**（`sugov_ext` 调频器） |
| 推理引擎 | **llama.cpp `b7050`（commit `dd091e5`）**，NDK **28.2.13676358**，`android-24`，静态/共享库自编 |
| 编译 | 两个变体：**基线**（默认 `-march`）与 **dotprod**（`GGML_CPU_ARM_ARCH=armv8.2-a+dotprod`） |
| 上下文 / 批 | `n_ctx = 2048`，`n_batch = 512` |
| 线程 | **4 线程 + 亲和性 `f0`（只用 cpu4–7 大核）**（理由见 §4） |
| 解码 | 贪心（`llama_sampler_init_greedy`），排除采样随机性 |
| prompt | `tool/llm_bench/prompts_finance.txt` 里 8 段中文财报问答，逐轮轮换（173–177 token） |
| 轮数 | 10 轮（每轮清空 KV，模拟 10 次独立提问） |

**口径**（`tool/llm_bench/bench_android.cpp` 里就是这几行，别在别处另算）：

- **冷加载** = `llama_model_load_from_file` 墙钟（含建页表，不含首次解码）；
- **首 token** = 首轮 prefill 完成并采样出第一个 token 的时间（第 1 轮，冷态）；
- **pp tok/s** = prompt 处理速率；**tg tok/s** = 除首 token 外的生成速率（10 轮均值）；
- **峰值 RSS** = `VmHWM`；**10 轮后 RSS** = 最后一轮 `VmRSS`；
- **温升** = 首末**电池温度**差（`dumpsys battery`）—— HyperOS 下 `/sys/class/thermal/**` 对 shell
  是 `Permission denied`，温度拿不到，这是本表最弱的一项，见 §7。

## 2. 基准表（dotprod 变体 / 4 大核 / 10 轮）

| 模型（量化） | 文件 | 冷加载 | 首 token | pp tok/s | tg tok/s | 峰值 RSS | 10 轮后 RSS | 温升 | 备注 |
|---|---|---|---|---|---|---|---|---|---|
| **Qwen2.5-1.5B-Instruct Q4_K_M** | 1066 MB | **1.70 s** | **5.07 s** | 36.4 | **7.4** | 1185 MB | 1184 MB | +0.2 ℃ | 中文回答最稳，见 §5 |
| Qwen3-1.7B Q4_K_M | 1056 MB | 1.63 s | 5.66 s | 32.2 | 6.6 | 1350 MB | 1348 MB | +0.6 ℃ | 默认开「思考」，本次 120 token 全被 `<think>` 吃光 |
| Gemma-3-1B-it Q4_K_M | 769 MB | 1.19 s | 3.51 s | **50.4** | **8.8** | **885 MB** | 883 MB | +0.2 ℃ | 最快最省，但中文算数不可靠，见 §5 |

**读法**：

- 「首 token」≈ **28 ms / token 上下文**。上下文 60 token → 1.7 s；177 token → 5.1 s。
  ⇒ 产品上必须把上下文压到 **≤80 token**，否则用户会以为「没反应」。
- 「tg tok/s」≈ 7.4 → 中文约 **2 字/秒**。这个速度只适合「一段话解释」，不适合聊天式来回。
- RSS 一行内**完全平**（1184 MB × 10 轮）⇒ **没有逐轮泄漏**；但常驻 1.2 GB 对 6 GB 机型已经吃紧。

## 3. 编译开关的影响（同一台机、同一模型、同一线程）

| 变体 | Qwen2.5-1.5B pp | tg | Qwen3-1.7B pp | tg |
|---|---|---|---|---|
| 基线（默认 `-march`） | 24.8 | 7.5 | 22.2 | 6.6 |
| **dotprod**（`armv8.2-a+dotprod`） | **36.4（+47%）** | 7.4 | **32.2（+45%）** | 6.6 |

结论：**只影响预填（算力密集），不影响生成（带宽密集）**。
产品打包必须开 dotprod —— 否则同样的手机、同样的模型，首 token 白白慢 45%。
⚠️ 但 `armv8.2-a+dotprod` 是**编译期硬编码**：给不支持的旧机（≤ A72）装会 **SIGILL**。
真要兼容就得走 llama.cpp 的 `GGML_CPU_ALL_VARIANTS`（多后端 + 运行时挑选），
或按 ABI/机型拆包 —— 这是阶段四的事，本表先记下这个约束。

## 4. 线程数与亲和性

| 配置 | 模型 / 变体 | pp | tg |
|---|---|---|---|
| 4 线程，**不绑核** | Qwen2.5-1.5B / 基线 | 23.6 | **5.9** |
| 4 线程，**绑大核**（`taskset f0`） | Qwen2.5-1.5B / 基线 | 24.8 | **7.5（+27%）** |
| 4 线程，绑大核 | Qwen2.5-1.5B / dotprod | 36.4 | 7.4 |
| **8 线程，全核**（`taskset ff`） | Qwen3-1.7B / dotprod | 32.0 | **3.7（腰斩）** |

（每行都标了模型与变体 —— 不同行不要跨着比绝对值，只比同一行内「绑核前后 / 线程数」的差。）

解释：llama.cpp 的 `-t 4` 只**开 4 个计算线程**，Android 调度器会把它们丢到哪一簇全看运气
（本机 cpu0–3 是小核）；一旦线程数超过大核数（8），小核参与同步屏障 → **生成速度直接减半**。

⇒ **App 端实现必须自己绑大核**：JNI 里对每个 worker 线程调 `sched_setaffinity`（自家线程、在应用 cpuset 内是允许的），
线程数 = 大核数（本机 4）。**不要用「设置里让用户调线程数」来糊这件事。**

## 5. 质量抽查（人工看，非量化）

同一条 prompt（预算 4000 / 已花 4520.36 / 餐饮 1280.50 / 购物 980 / 居住 1500 / 剩 6 天），`--temp 0.3`：

| 模型 | 输出（摘录） | 判定 |
|---|---|---|
| **Qwen2.5-1.5B** | 「本月超支 **520.36** 元，剩余 6 天最多还能花 **141.21** 元。」 | 超支算对；**每日额度是编的**（真实口径应为 0，已超支） |
| Qwen3-1.7B | `<think>` 里做了 3 次加法，120 token 用完还没出答案 | **默认思考模式 = token 预算杀手**；要接必须关 thinking 并单独测 |
| Gemma-3-1B | 「已经超支了 **4520.36** 元……每天最多花 **4000** 元」 | 数字全错（把总支出当超支额），中文表达也生硬 |

**这三条一起说明一件事**（也正是 SPEC 的设计前提）：
**模型会算错数，且错得很自然**。所以架构上必须

1. 所有金额/占比/环比**由 Dart 侧既有纯函数算好**（`summarize` / `categoryBreakdown` /
   `buildBudgetView` / `monthlyTrend`），以「事实清单」形式塞进上下文；
2. 模型的职责只是**把事实改写成中文**，且**回答里出现的数字要能和事实清单对上**（校验后才展示）；
3. 算不出/没有数据时明确说「没有这笔数据」，不许补。

## 6. 20 分钟连续推理（温升与降频）

条件：Qwen2.5-1.5B Q4_K_M / dotprod / 4 线程绑大核 / `--minutes 20`，一轮接一轮不休息（共 **68 轮**）。

| 指标 | 开机段（第 1–3 轮） | 结束段（第 66–68 轮） | 结论 |
|---|---|---|---|
| tg tok/s | 7.47 / 7.05 / 7.34 | 7.25 / 7.31 / **7.42** | **没有掉速**（抖动在 ±0.2 内） |
| pp tok/s | 31.5 → 35.5 | 32.5 → 32.9 | 略降 5–8% |
| 大核频率 | 2850 MHz（峰值） | **稳定 2150 MHz** | 降频 **−24%**，但吞吐没掉 |
| 电池温度 | 37.2 ℃ | **38.6 ℃** | +1.4 ℃（代理指标，见 §8） |
| VmRSS | 1183 MB | **1038 MB** | 不升反降（页缓存被回收；`VmHWM` 恒 1185 MB） |

**解读**：手机在连续 20 分钟后确实从 2.85 GHz 掉到 2.15 GHz，但 **tg 没变** ——
说明瓶颈在**内存带宽**（每生成 1 个 token 要读约 1 GB 权重），不是算力。
⇒ 这也是「为什么 dotprod 只提速预填、不提速生成」的同一个原因。
⇒ 产品上不必为「跑久了变慢」做降级，真正要防的是**内存**（1.2 GB 常驻）与**首 token 的上下文长度**。

## 7. 复现

```powershell
# 1) 编端上探针（首次会浅克隆 llama.cpp 到 D:\yanxin-llm-bench，约 2–3 分钟；产物不进库）
powershell -File tool/llm_bench/build_android.ps1                                   # 基线变体
powershell -File tool/llm_bench/build_android.ps1 -BuildDir build-arm64-dp `
    -OutDir out-dp -ArmArch 'armv8.2-a+dotprod'                                     # dotprod 变体

# 2) 模型：从 ModelScope 下（HF 在本机不可达），已校验 sha256
#    Qwen2.5-1.5B-Instruct-GGUF / qwen2.5-1.5b-instruct-q4_k_m.gguf  1066 MB  6a1a2eb6…
#    unsloth/Qwen3-1.7B-GGUF / Qwen3-1.7B-Q4_K_M.gguf                1056 MB  b139949c…
#    unsloth/gemma-3-1b-it-GGUF / gemma-3-1b-it-Q4_K_M.gguf           769 MB   8270790f…

# 3) 跑（自动推探针 + 模型、按字节数跳过重复推送、主机侧每 15 s 采温度/频率）
powershell -File tool/llm_bench/run_bench.ps1 `
  -ModelPath D:\yanxin-llm-bench\models\qwen2.5-1.5b-instruct-q4_k_m.gguf `
  -Label 'Qwen2.5-1.5B-Instruct Q4_K_M' -CpuMask f0 -Threads 4 -Rounds 10 `
  -OutDir out-dp -Remote /data/local/tmp/llmbench-dp

# 4) 长跑（看温升与降频）
powershell -File tool/llm_bench/run_bench.ps1 ... -Minutes 20
```

原始日志落在 `$WorkRoot\out(-dp)\raw-*.txt`（不进库，含每轮 ttft/rss/频率）。

## 8. 已知限制（别把这张表读超了）

| # | 项 | 说明 |
|---|---|---|
| 1 | **温度是电池温度代理** | HyperOS 屏蔽了 thermal_zone；电池温度滞后、量级偏小（10 轮 +0.2–0.6 ℃、20 分钟 +1.4 ℃ 都不代表 SoC 没热，只能看趋势） |
| 2 | 频率采样是**主机侧每 15 s 一次** | 只能看出「有没有掉到低频」，看不出瞬时降频；`200 MHz` 这种值是轮间隙的空闲采样 |
| 3 | 质量抽查只有 **1 条 prompt × 3 个模型** | 只能证明「会算错」，不能证明谁最准；正式选型需要 20+ 条真实问题集 |
| 4 | 只测了 **1 台设备** | SPEC §6 要求「3 个模型 × 2 台设备」；第二台（低端机）还没有 |
| 5 | 没测 **Stage-3 需要的 JSON 约束 / 工具调用** | llama.cpp 的 grammar 会对 tok/s 有影响，届时重测 |
| 6 | 没测 **后台/锁屏** 场景 | Android 会限流，真实可用性要单独验 |

## 9. 对后续实现的三条硬约束（从本表直接得出）

1. **数字只从 Dart 来**：上下文里的金额/占比全部由既有纯函数产出，模型只做措辞；
2. **线程绑大核 + 编译开 dotprod**：否则首 token 慢 45%、生成慢 27%；
3. **上下文预算 ≤ 80 token 才算「秒回」**：这反过来要求「先查询再提问」——
   把 4–6 个关键数字压成事实清单，而不是把流水全塞给模型。
